# ROP-Insight P6/P7 精简版开发设计文档

## 1. 项目背景与目标

ROP-Insight 是基于 Python 3.12、PyQt6 开发的 Windows 本地 ROP 眼底图像分析研究原型。

系统目前已实现眼底图像导入与交互、Ridge/Vessel 结构分析、ROP 四分类、结构量化、严重程度评分、辅助分类、分析结果导出及 P5 文字报告生成。

本阶段在现有系统基础上实现两个功能模块：

- **P6：病例与数据管理**，实现病例创建、图像关联、分析结果及报告保存。
- **P7：历史记录管理**，实现历史查询、结果查看和报告重开。

核心目标是形成完整的：

**创建病例 → 导入图像 → 执行分析 → 保存结果 → 查询历史 → 查看结果**

不修改模型、算法及现有分析流程。

## 2. 技术方案

### 2.1 存储方式

建议采用三部分组成的轻量化数据管理方案。

| 组件 | 职责 |
|---|---|
| SQLite | 保存病例信息、分析记录及文件索引 |
| JSON | 保存完整分析结果及模型参数 |
| 文件系统 | 保存眼底原图、Mask、可视化图像及 P5 报告 |

使用 Python 标准库 `sqlite3`，不新增数据库服务器或第三方 ORM。

优先复用 P4/P5 已实现的 JSON、报告导出、文件校验及哈希机制。

### 2.2 简化数据模型

建议采用两张主要数据表。

**表一：cases（病例信息）**

| 字段 | 说明 |
|---|---|
| case_id | 系统生成的内部唯一 ID |
| case_code | 用户填写的匿名病例编号，唯一 |
| eye | 左眼、右眼或未指定 |
| exam_date | 检查日期 |
| created_at | 创建时间 |

**表二：analysis_records（分析记录）**

| 字段 | 说明 |
|---|---|
| record_id | 分析记录唯一 ID |
| case_id | 关联病例 ID |
| image_path | 托管原图路径 |
| result_path | 分析结果 JSON 路径 |
| report_path | P5 报告路径，可为空 |
| status | 分析及保存状态 |
| created_at | 记录创建时间 |

说明：

1. 一条分析记录对应一次单张图像分析。
2. 一个病例可保存多次分析记录，但不实现多图聚合。
3. 相同图像重复分析时创建新记录，不覆盖旧记录。
4. 病例信息修改不应改变历史分析结果。
5. 模型版本、量化指标、各模块状态等详细信息继续保存在现有 JSON 中。

若现有工程已经具备适用的数据结构，应优先复用，不强制新建上述表。

### 2.3 文件目录

建议在用户可选择的本地数据目录中保存：

```text
ROP_Insight_Data/
├── rop_insight.db
└── records/
    ├── <record_id>/
    │   ├── original.png
    │   ├── result.json
    │   ├── masks/
    │   ├── overlays/
    │   └── report/
    └── ...
```

要求：

- 原图保存独立副本，避免用户移动或删除源文件后无法查看。
- 保留原文件格式，不强制转换 PNG。
- 分析结果沿用现有 JSON 格式。
- 相关文件路径使用数据根目录下的相对路径。
- 文件保存完成并校验后，才将记录标记为可读取。
- 不覆盖已有记录及报告。

本阶段只实现必要的文件完整性检查，不开发复杂恢复工具。

# 3. P6：病例与数据管理

## 3.1 病例创建

用户可在界面中创建研究病例。

输入字段：

| 字段 | 要求 |
|---|---|
| 病例编号 | 必填，匿名研究编号 |
| 左右眼 | 左眼、右眼、未指定 |
| 检查日期 | 可选，默认当天 |
| 创建时间 | 系统自动生成 |

功能要求：

1. 检查病例编号是否为空或重复。
2. 创建成功后显示当前病例编号。
3. 支持选择已有病例。
4. 保留现有病例信息界面，尽量只做必要调整。

当前版本不增加姓名、身份证号、联系电话等个人敏感字段。

## 3.2 图像与病例关联

用户选择病例后导入眼底图像，将该图像与当前病例关联。

要求：

1. 图像导入后能够显示所属病例编号。
2. 不修改现有图像加载及预览流程。
3. 执行分析时固定本次分析所属病例和图像。
4. 切换病例或图像时，不得将旧分析结果关联到新病例。
5. 未选择病例时，保留原有临时分析功能，不强制创建病例。

## 3.3 分析结果保存

对已选择病例的分析，提供“保存记录”功能。

保存内容包括：

- 当前眼底原图副本。
- 分析结果 JSON。
- 已生成的 Ridge/Vessel Mask。
- 已生成的叠加可视化图像。
- 已生成的 P5 文字报告及 PDF 等文件。
- 病例与分析记录的关联信息。

要求：

1. 直接调用现有 P4/P5 导出服务，不重新实现算法结果序列化。
2. 允许部分成功结果保存，但必须保留失败模块及原因。
3. 报告尚未生成时允许保存分析记录，报告路径为空。
4. 后续可以为该分析记录补充保存报告。
5. 相同记录重复点击保存不得产生重复历史条目。
6. 保存失败时提示原因，不生成指向缺失文件的有效记录。

本版本采用**用户主动保存**，暂不实现复杂的自动保存任务生命周期。

## 3.4 P6 界面设计

优先利用现有界面。

建议增加：

- “新建病例”入口。
- “选择病例”入口。
- 当前病例基本信息显示。
- “保存分析记录”按钮。
- 保存成功或失败状态提示。

不重新设计软件主窗口。

## 3.5 P6 验收要求

1. 能够创建并读取病例。
2. 能够将当前图像关联到病例。
3. 能够保存分析结果及已有报告。
4. 软件重启后病例和记录仍然存在。
5. 删除原始导入位置的文件后，已保存图像仍可打开。
6. 同一图像多次分析能够独立保存。
7. 切换病例或图像不会产生错误关联。
8. 保存失败不影响现有分析结果。

# 4. P7：历史记录管理

## 4.1 历史记录列表

增加或完善历史分析界面。

列表至少显示：

| 字段 | 内容 |
|---|---|
| 病例编号 | 匿名研究编号 |
| 左右眼 | 左眼/右眼/未指定 |
| 检查日期 | 病例检查日期 |
| 分析时间 | 本次分析时间 |
| 预测分期 | A6 预测结果，缺失时显示不可用 |
| 状态 | 成功、部分成功、失败等 |

默认按照分析时间倒序排列。

无记录时显示空状态，而不是错误提示。

## 4.2 历史记录查询

提供简单的病例编号搜索框。

要求：

1. 输入病例编号后筛选对应历史记录。
2. 清空搜索框恢复完整列表。
3. 支持查询不存在的病例编号并显示无结果。
4. 暂不增加复杂筛选和组合查询。

## 4.3 历史结果查看

用户选择某条历史记录后，可以查看：

- 原始眼底图像。
- Ridge/Vessel Mask 及叠加图。
- A6 四分类预测及概率。
- 病理结构量化指标。
- 连续严重程度评分及后验区间。
- SVM 辅助分类结果。
- 本次分析的状态及不可用原因。

要求：

1. 从已保存的 JSON 和图像工件恢复结果。
2. 不重新调用分类、分割或量化模型。
3. 恢复结果不得覆盖其他历史记录。
4. 缺少部分文件时提供明确提示，不使用其他记录的结果填补。
5. 保留模型版本和输入来源信息。

## 4.4 历史报告查看

在历史记录详情中增加“查看报告”入口。

功能要求：

- 打开已经保存的 P5 报告。
- 支持查看报告正文。
- 支持打开或导出已有 PDF。
- 没有报告时显示“未生成报告”。
- 不修改旧报告内容，不自动生成新的诊断文字。

## 4.5 P7 界面设计

建议采用：

**左侧历史记录列表 + 右侧分析详情**

也可以复用现有历史管理窗口，不强制改变其布局。

至少提供：

- 病例编号搜索。
- 历史记录列表。
- 查看分析结果。
- 查看报告。
- 返回当前分析界面。

本阶段不实现多次分析对比、归档、批量删除或复杂数据库管理。

## 4.6 P7 验收要求

1. 软件重启后能够正常查询历史。
2. 病例编号搜索结果正确。
3. 能够加载历史图像和分析结果。
4. 能够打开对应 P5 报告。
5. 历史结果加载不触发模型推理。
6. 缺失文件或损坏 JSON 时能够提示异常。
7. 多条记录之间不存在结果串用。
8. 不影响当前正常分析流程。

# 5. 开发阶段与执行顺序

建议划分为四个小任务。

| 阶段 | 开发内容 | 验收目标 |
|---|---|---|
| P6-A | 简化数据模型和存储接口 | 数据库创建、病例读写、结果路径关联 |
| P6-B | 病例界面与结果保存 | 能够完整保存一条病例分析记录 |
| P7-A | 历史列表与搜索 | 能够查询已有记录 |
| P7-B | 历史结果及报告恢复 | 能够重新查看完整分析内容 |

每个阶段独立验收，不一次性开发全部功能。

---

# 6. 技术约束

1. 保留现有 P1—P5 及轻量 P6/P7 已完成功能。
2. 优先复用已有病例、历史、报告与导出代码。
3. 不重新训练或修改任何模型。
4. 不修改已验证的分类、分割、量化逻辑。
5. 不改变现有 P4/P5 JSON 与报告数据格式。
6. 不引入 MySQL、Web 服务或远程数据库。
7. 不实现多图聚合。
8. 不实现复杂病例版本管理、自动备份、多层故障恢复。
9. 不擅自安装依赖或修改实验环境。
10. SQLite 数据库存取不得长时间阻塞 GUI 主线程。
11. 不因功能精简而取消基本的数据完整性和异常处理。
12. 对现有代码的修改以实现本次需求所必需的最小范围为准。

# 7. 测试要求

至少完成以下测试：

- 病例创建、重复编号、读取。
- 病例与图像关联。
- 分析结果及报告保存。
- 同一图像多次分析独立存储。
- 重复保存不产生重复记录。
- 软件重启后的数据读取。
- 源文件删除后的托管图像读取。
- 历史列表及编号搜索。
- 历史结果和报告恢复。
- 缺失文件、损坏 JSON、保存失败处理。
- 换图、换病例时的结果隔离。
- 原有功能回归测试。

测试时使用临时目录和模拟病例，不直接修改或删除真实研究数据。

# 8. 开发过程要求

按照既定 AI 协同开发流程执行：

1. 阅读现有代码和项目规则。
2. 核对现有 P6/P7 已实现的功能。
3. 制定最小修改方案。
4. 人工审核后分步编码。
5. 检查 Git Diff。
6. 运行新增测试及回归测试。
7. 更新开发记录并提交 Git。

注意：此前已经形成过复杂的 P6 五表数据库设计，但**本次精简版需求优先级更高**。

如果复杂方案尚未开始编码，则不继续实施；如果已有部分实现，则先检查并提出最小兼容或调整方案，不擅自删除现有代码或数据。

# 9. 本轮实施计划（当前用户授权优先）

用户已明确授权：先修订文档，再实现精简P6-A、P6-B；附件旧版“仅计划”指令不作为本轮停止条件。以61dc1ed的P5工作台为基线，旧五表方案和独立托管入口不恢复；旧代码仅保留Git备份，不迁移旧数据库或删除本地数据。

- P6-A：标准库sqlite3实现cases、analysis_records两表；编号去首尾空白后不区分ASCII大小写唯一；日期可空，界面默认当天。记录按run_id唯一，主动保存，原图原字节副本，P4/P5服务原样调用，采用同盘临时写入/哈希校验/目录发布后短事务登记。保存失败不生成有效索引；发布后登记失败保留文件，同请求可验证后重试。
- P6-B：在现有工作台增加“病例与资料库”和“保存分析记录”。数据库操作及复制/报告保存用现有后台线程。分析开始冻结病例与图像；切换病例后旧结果不能保存到新病例；未选病例仍可临时分析。先保存无报告记录，预览报告后再次保存可补充报告，不覆盖旧报告。数据库文件存用户明确选择目录，不自动创建在源码中。
- P7-A：后续实现历史列表、病例编号搜索；本轮不开发。
- P7-B：后续从保存文件恢复图像/结果/报告，不推理；本轮不开发。

额外索引字段仅用于run_id幂等、文件清单哈希及报告哈希，不引入第三张表、病例版本、后台自动保存、备份恢复或P8。完整结果以现有JSON为准。历史病例快照独立保存在记录管理清单，不修改P4/P5契约。

本轮文件：services/local_records.py，ui/case_selector.py及main_window最小接入；新增存储及UI测试。验证病例创建/重复/重启、源删除、重复/多Run保存、报告补充、失败/损坏/越界、换图换病例、后台与安全关闭、既有回归。每段测试通过后提交Git，完成P6-B后停止。
