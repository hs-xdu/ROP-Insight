## 2. 审核决定与字段归属

| 实体 | 权威字段 | 修改影响 |
| --- | --- | --- |
| Case | 内部病例UUID、匿名研究编号、创建/更新时间、当前病例资料版本 | 更新仅追加病例版本并切换当前指针 |
| Image | 持久化图像UUID、所属病例、眼别、检查日期、图像名/路径/尺寸/格式/哈希/导入时间 | 登记时独立保存；不动态读取病例默认值 |

保留 case_revisions：记录研究编号、病例备注及可选眼别/日期默认值的历史。默认值仅用于创建或关联图像时预填，不是历史图像或运行的事实来源。病例修改不得级联更新 Image、Run、旧报告或旧JSON。Image修正不原地改变已有分析的输入身份；本期采取显式新增图像关联记录，旧记录保留。

病例编号在同一仓库中唯一：去首尾空白，沿用1—64字符ASCII字母、数字、下划线/连字符且首位字母/数字；以小写规范键判重，保留显示形式。内部UUID永久不变。双眼及多次检查共用病例UUID，眼别、日期归各自Image。旧资料同编号不自动合并。

## 3. 数据架构与文件布局

维持五表：cases、case_revisions、images、analysis_runs、artifacts。SQLite保存身份、关联、状态和必要查询索引；JSON保存完整结果/模块参数/模型版本/错误；文件系统保存原图、输入Ridge、Mask、叠加图及报告。数据库不重复存完整预测与特征数据。

用户选择专用本地仓库，建议布局：

```text
数据根目录/
  catalog.sqlite3
  images/<image_uuid>/original.<原格式>
  images/<image_uuid>/image_manifest.json
  runs/<run_uuid>/inputs/
  runs/<run_uuid>/analysis/<P4导出包>/
  runs/<run_uuid>/reports/<report_id>/<P5报告包>/
  runs/<run_uuid>/run_manifest.json
  .staging/<operation_uuid>/
```

原图按原字节托管，不重编码；核对原文件及解码像素哈希，防止加载后源文件变化。原始文件名仅作为资料保存，不自动带入便携报告。输入Ridge原文件与规范化输出Mask区分登记。路径相对仓库根目录，拒绝越界、链接/重解析点及外部URL。同一登记图像多次分析复用原图；跨病例不凭哈希自动合并。

## 4. 自动保存策略

- 未建立病例、未完成图像托管：保留当前临时分析和手动导出行为，不自动新建托管病例或强制落库。现有临时匿名显示编号不等同于数据库已有Case。
- 已建立病例且图像托管通过：启动前冻结关联并登记Run，终态自动保存。
- success / partial_success：保存实际可用结果、模块状态、错误及已有工件，复用P4导出；部分失败值保持缺失/不可用，禁止补成0或正常。
- failed / cancelled：允许仅保存运行/模块状态、错误、输入来源及已取得工件，不强制完整P4包。最小终态JSON与run_manifest必须写入并校验；没有Mask/报告须明确记为未生成。
- 报告仍由用户主动生成并保存，复用P5流程，关联准确Run。报告写入失败不更改分析终态或已保存分析，允许稍后重试。
- 换图、切换病例及晚到回调不能更换已冻结关联；正常关闭等待取消和必要终态保存结束。

## 5. 分层一致性保障

### 前期必须具备的底线

从P6-A开始具备数据库事务、外键、唯一性、版本并发检查和回滚；从P6-B第一个文件保存操作开始，同时具备文件读回/哈希校验、保存状态、幂等、异常检测。不得等到P6-F才保证这些正确性。

分析状态与保存状态、完整性状态分开：分析沿用running/success/partial_success/failed/cancelled；保存使用pending/saving/ready/write_failed；完整性使用unchecked/valid/missing/corrupt。ready只表示该类保存契约完整发布，不代表算法成功或全部模块都有输出。有效读取要求ready且完整性valid；失败/取消可为“有效的失败/取消记录”，不能显示为成功分析。

文件保存采用短事务和分步发布：登记pending及operation_id → 临时目录写文件 → 校验 → 同盘目录重命名 → 事务登记工件和ready。文件复制/哈希不在SQLite长事务内。相同业务ID及相同内容摘要重试为幂等；相同ID不同内容报冲突。

发布后数据库提交失败：保持pending/saving或write_failed，不标ready；文件保留供核对，不盲删。启动时检测未完成状态并阻止当作有效记录读取；前期可提示人工处理或安全重试，不承诺自动修复。

### P6-F 增强能力

完整备份/恢复、孤立目录盘点与受控修复、跨数据库与文件的恢复报告集中在P6-F。使用SQLite Backup API和写入协调边界，备份数据库及已发布文件并核对清单；恢复到新目录验证后启用。不得把直接复制正在写入的数据库视为完整备份。

P6-A保留迁移版本号与事务升级/失败回滚；本轮A不提供自动升级既有生产库。引入后续真实迁移前必须具备可靠备份或经核对的离线备份流程。

## 6. P5兼容与旧数据

保留P4 schema_version=1、P5 report_schema_version=1及固定模板；管理UUID、路径、运行保存状态放数据库和独立管理清单，不改原报告数据契约。P5 source_snapshot_sha256沿用既有字段投影，与整个result.json文件SHA256区分。

原CaseMetadata字段集严格校验，不直接新增数据库字段；由适配层以Run冻结的病例版本和Image信息构造旧格式病例快照。旧病例/图像ID保留源身份，通过索引映射管理ID。病例默认值不覆盖Image事实。

一个Run可有多份报告，不因新报告再建Run；旧报告不回写、不用新模板替代。success/partial_success持久化仍用P4包；失败/取消的管理用最小JSON是独立版本格式，不冒充完整P4包，不强制旧history_store把它当作P4分析包。

旧成果显式校验后登记/托管，不自动全盘迁移。缺原图或病例冲突明确标记，不能宣称可完整恢复。原P7目录式浏览保留，本期不新增完整P7恢复、对比、删除界面。
